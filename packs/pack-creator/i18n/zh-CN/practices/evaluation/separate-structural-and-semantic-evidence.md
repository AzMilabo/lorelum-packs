# 不同检查结果只能证明各自观察到的事情

## 适用场景

准备把多种校验或评估结果汇总成 Pack 就绪结论时使用。先分别判断每项结果支持什么。常见四层是文件结构有效、人工判断内容质量、实际查询选中了什么，以及 Agent 收到 Practice 后怎样行动。

## 具体指导

分组记录证据：结构检查只覆盖 frontmatter、路径、ID 唯一性和目录覆盖；语义审查记录领域人员是否认可 trigger、动作、错误机制、例外和示例；召回证据记录特定系统对明确查询选了哪些 Practice；行为证据记录代表性 Agent 收到内容后是否作出更好决定。每条结论都写明类别、Pack
revision 和实际观察。未测试更强层级时使用窄措辞。直到每个就绪声明都指向能支持它的证据，不把各组平均成质量分数。

## 反模式

无障碍 Pack 的 schema
validator 通过，所有目录 ID 都有测试数据，文件也可解析。发布清单需要简单答案，结构结果又客观，作者便报告“指导完整且召回正确”。实际上没有无障碍专家审查内容、没有运行召回系统，也没有 Agent 任务使用这些指导。

## 原因

每类证据回答不同问题。混在一起会隐藏未知，也让后来者无法判断失败来自文件、内容、选择还是使用行为。

## 例外与边界

一个实验直接观察多个层级时可以同时产生多类证据，但应分别记录。专家审查仍是判断，不等于召回行为；一次 Agent 任务也不能证明广泛内容覆盖。本条只分类证据，不规定工具或 benchmark 大小。

## 示例

隐私 Pack 先通过 schema 与 ID 检查；两名隐私工程师发现删除条目的例外过宽并修正；随后召回测试区分了删除与保留查询；小型 Agent 任务又漏掉仓库特有审批步骤。作者分别报告四项结果，而不笼统称“Pack 已验证”。
