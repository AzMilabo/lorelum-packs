# 只纳入当前有依据的工作

## 适用场景

在决定哪些拟议事项应进入已承诺的计划时，应用本条 Practice。触发条件是某项工作看似合理，但当前依据尚不确定；不是某个公共表面变更已经进入实现阶段。本条 Practice 审查所有候选工作，并不代替后续针对特定接口或扩展点的设计检查。

## 具体指导

为每个候选事项给出一种范围归类：必需、可选或超出范围。只有当它直接支持当前验收条件、有证据支撑的风险、稳定契约或已明确批准的扩展时，才将其标为必需。缺少这些依据的有用想法仍然是可选项，不得成为实现依赖。如果其状态取决于尚未作出的权威决策，应保留为未决并请求该决策，而不是默认将其升级。当每个已承诺事项都有当前可追溯的理由时停止。

## 反模式

一项只要求支持单一数据源的计划，为了“更灵活”而加入任意文件定位器和网络定位器。虽然没有当前用户、契约或风险要求这些额外定位器，它们却成了必做工作。

## 原因

范围在计划阶段扩张的成本最低，但在代码、测试和兼容性预期附着之后代价最高。要求当前依据，可以阻止“功能更多”或“抽象更多”之类的替代性成果挤占所请求的结果。

## 例外与边界

即使功能请求没有点名，安全、隐私、数据完整性、兼容性和合规保护也可能因有证据的风险或治理契约而成为必需项。反过来，本条 Practice 并不禁止记录可选改进；它防止这些改进悄然变成承诺。

## 示例

对于一项明确只要求一个自定义 Registry 的任务，将狭义 Registry 路径纳入必需范围。把支持任意定位器记录为可选，因为“将来可能有用”并不是当前依据。
