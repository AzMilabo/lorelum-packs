# 旧的测试结果只能用于它仍然覆盖的文件和环境

## 适用场景

代码、配置、依赖、构建产物、运行环境或相关外部服务可能已变化，而 Agent 想引用此前通过结果时使用。要判断旧结果是否仍描述现在要交付的东西。它不同于“结果覆盖哪项验收”和“完全缺结果时怎么办”。

## 具体指导

对每项结果写清：测试的是哪次 commit 或 diff、哪个构建或生成文件、相关配置和依赖版本、必要时是哪台机器或服务、会变化的外部事实在何时观察，以及实际执行了什么行为。与当前交付物逐项比较，标为现在可用、已过期或不受后续变化影响，并说明原因。只重跑结论可能变化的检查；实际交付文件改变时必须重建重验。

## 反模式

用户要求归档能被另一应用打开。兼容检查通过后，Agent 又做一次看似机械的序列化清理。外部检查很慢，复用旧结果很诱人；但最终字节来自旧结果从未执行的新代码。

## 原因

通过结果描述特定文件在特定条件下的表现，不是贴在任务上的永久徽章。记录这些具体关系，既防止旧结果证明新文件，也避免无关变更导致全部重跑。

## 例外与边界

前提未变的事实可在无关修改后继续使用，例如文档修改通常不影响 parser 单测；parser 代码变化则使旧二进制文件测试失效。安全、破坏性操作、发布和依赖实时环境的结果通常要求更新。项目强制重跑规则优先。

## 示例

commit A 构建的 CLI 二进制文件通过真实 Pack 安装。之后只改注释，结果仍可用；commit
B 修改参数解析后，Agent 重建二进制文件并重跑安装。B 上的源码单测不能证明 A 的旧二进制文件代表当前代码。
