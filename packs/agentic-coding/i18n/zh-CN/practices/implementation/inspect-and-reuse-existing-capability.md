# 构建前先复用现有能力

## 适用场景

在准备为某项能力创建新实现，而该能力很可能已存在于 runtime、已声明依赖、相关模块或其测试中时，立即应用本条 Practice。这是一次复用决策，不是泛化的搜索仪式。如果当前证据已经表明该能力有意作为全新能力，或现有选项无法满足某项必需约束，则不适用。

## 具体指导

检查能够回答复用问题的最小证据集合：相关模块边界、其调用点与测试，然后是最可能拥有该能力的 runtime 或依赖。决定直接复用、做小幅适配，还是创建新实现。记录排除每个更接近现状的选项所依据的约束。当证据足以区分这些选择时停止搜索；输出是一项复用决策，而不是备选方案目录。

## 反模式

凭记忆编写 parser、validator、重试循环、cache 或抽象，因为它看起来很容易实现，之后才发现项目已经带有等价能力，只是其边界情况行为不同。

## 原因

现有能力通常编码了兼容性、失败语义和维护所有权，而这些在新的局部实现中不可见。构建前检查，可以避免并行契约，并让新代码只覆盖当前需求真正超出现有能力的部分。

## 例外与边界

不要仅因名称相同就复用某项能力。安全边界、许可证限制、不支持的环境、不稳定 API 或已证实的语义不匹配，都可以成为新建实现的正当理由。在多个已经可行的设计之间选择，属于设计选择；本条 Practice 只负责确认复用是否是有效的首选方案。

## 示例

在添加自定义版本比较逻辑前，Agent 发现项目 runtime 已提供所需 prerelease 语义的比较功能。可观察的决策是“复用 runtime 函数”，不新增 comparator 或 wrapper。
