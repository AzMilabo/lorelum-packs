# 显式记录可安全采用的未确认假设

## 适用场景

当某项具体不确定性仍然存在、其暂定解释的影响有限且可逆，而且实现可以安全继续时，应用本条 Practice。如果未知项会改变公共契约、产品行为、安全边界、不可逆迁移或其他高成本决策，则属于近似但不同的场景；这种不确定性必须在实现前得到确认，而不能仅仅披露。

## 具体指导

创建一条明确的假设记录，其中包含暂定解释、当前支持它的证据、受影响的实现边界，以及确认或推翻它的条件。把实现限制在该边界内，不要从这一假设继续推导更多需求。输出是可见的假设及其审查触发条件；当后续工作无需重建探索过程，就能识别并替换它时停止。

## 反模式

选择一个看似合理的默认值，围绕它实现多个相互依赖的行为，然后把结果描述成必需行为，尽管来源材料从未确定该选择。

## 原因

未说出口的假设很容易被后续代码、测试、摘要或交接升级为事实。显式记录可以保留不确定性并限制其传播，同时仍允许低风险工作继续。

## 例外与边界

不要用假设记录绕过相互冲突的权威来源，或绕过需要产品、安全、法律或运营批准的决策。完全由现有约定决定的纯局部实现细节不需要额外仪式。如果新证据推翻了假设，应修订受影响的工作，而不是把该假设保留为兼容行为。

## 示例

某个 API 示例没有说明时间戳是否包含小数秒，而当前所有响应都使用整数秒，且解析逻辑可以容忍两者。Agent 记录“在契约确认前输出整数秒”，把该选择限制在序列化层，并将契约澄清设为审查触发条件。
