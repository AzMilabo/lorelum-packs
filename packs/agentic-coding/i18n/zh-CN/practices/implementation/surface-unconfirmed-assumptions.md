# 把安全且临时的假设明确写出来

## 适用场景

某个具体细节尚未确定，但两种合理选择都安全、局部且容易替换时使用。它不能改变用户可见含义、公共契约、安全边界或不可逆操作；这些高影响选择必须先确认。若多份有效要求互相冲突，应先确认听谁的。

## 具体指导

记录暂时采用的解释、为何合理、准确影响哪些代码，以及未来什么回答或证据会确认或替换它。依赖工作只能留在这条边界内，不能从假设继续推导新需求。写到另一名工程师不用重放调查就能找到、审查和替换该选择时停止。

## 反模式

新导入器的样例没出现空描述，共享模型同时接受缺失值和空字符串。只在导入器用空字符串快速且无害，但 Agent 为“一致”又修改共享序列化器和测试。一个局部临时选择因此扩散到所有导入器，看起来像已接受的数据契约。

## 原因

代码和测试会让没写明的选择看似已经定案。明确记录能保留不确定性、限制传播，同时允许安全推进。

## 例外与边界

不能用临时假设绕过冲突需求，或产品、安全、法律和运营必须批准的决定。仓库惯例已确定的细节不需额外记录。新证据推翻假设时，修改限定范围内的实现，不要为猜测保兼容。

## 示例

样例未说明空的可选标签应省略还是传空字符串，而 parser 两者都接受。Agent 记录“暂时省略字段”，只影响一个序列化器，并把已接受 schema 的澄清作为复核条件。
