# 暂停前写一份能保住关键决定的 Checkpoint

## 适用场景

已知即将发生上下文缩减、长暂停或跨会话，需要给未来工作留短恢复记录时使用。Checkpoint 要在中断前存到恢复任务能读取的位置；上下文已经丢失后不能凭记忆补写，应重读请求、文件和结果。

## 具体指导

记录用户当前目标；决定工作的准确用户要求、已接受 Issue、规格或计划；已接受决定及其对下一步的限制；第一项尚未完成的必需行为；仍对应当前 commit 或文件的测试和审查结果；未确认的风险、阻塞问题和假设；以及下一项有依据的行动。链接改动文件和完整日志，不复制大段内容；失败实验和被否决方案只保留“为何不能再走”。冷启动读者能知道重开什么、完成什么、缺什么、不能假设什么和从哪里继续时停止。

## 反模式

用户只授权诊断授权失败。临近上下文上限时，Agent 把最近命令输出、编辑过的文件和一个看似有希望的缓存修复写进 Checkpoint，因为这些最具体；却漏掉“未授权实现”、拒绝路径未验证，以及缓存解释只是猜测。恢复后的会话很可能直接编码这个猜测。

## 原因

恢复会话需要的是决定工作和限制工作的事实，不是最近活动摘要。把请求、决定、缺失行为和限制放在显眼位置，能避免日志或诱人假设带偏下一步。

## 例外与边界

事故、审计、法律或可复现性要求的完整日志单独保留，Checkpoint 只链接。短小无状态任务可只写一句。Checkpoint 也不能让新 Agent 免于验证其他 Agent 的结论。

## 示例

存储迁移必须在不丢现有行的情况下回滚。暂停前，Agent 记录已接受迁移文档、保留旧读取器直到回滚被证明的决定、当前改动文件，以及当前 commit 正向迁移通过；明确“有数据回滚未运行”，链接完整输出，并记下两个方案因过早改写行而被否决。下一步是有数据回滚检查，不是代码清理。
