# 编写决策密集的 Checkpoint

## 适用场景

在已知中断或上下文边界到来前，当下一轮推理需要一份紧凑的恢复产物时，应用本条 Practice。不要在上下文已经丢失后应用；此时必须从持久来源重新立足事实，而不能信任刚刚重建的 checkpoint。

## 具体指导

编写一份 checkpoint，其中包含当前目标、权威来源、验收边界、已接受决策、未完成范围、仍有效的证据，以及重大风险或未知项。将已否决选项、失败实验和冗长输出压缩为只保留那些约束未来决策的结论；标记不确定性，而不是把它转化为事实。当 checkpoint 能够引导重新阅读和继续工作，同时不必保留完整过程 transcript 时停止。

## 反模式

记录每个被修改文件和最近的测试日志，却遗漏授权拒绝仍未验证，或者表面上的领域模型只是未经确认的实现假设。

## 原因

未来推理会受到 checkpoint 所突出内容的引导。保留决策输入和未解决边界，同时压缩探索过程，可以减少污染，又不丢失正确继续工作所需的事实。

## 例外与边界

如果事件响应、审计、法律或可复现性要求保留完整日志，应将日志单独保存；checkpoint 应指向这些证据，而不是把它们全部嵌入。非常短且无状态的任务，如果没有需要保留的实质决策状态，可能只需一句话。

## 示例

一份 checkpoint 说明目标是可恢复的媒体处理，列出当前规格，记录已接受的分块 pipeline，注明取消清理尚未验证，并链接最新的有效结果。它把两个失败方案压缩为“因将完整输入保留在内存中而被否决”。
