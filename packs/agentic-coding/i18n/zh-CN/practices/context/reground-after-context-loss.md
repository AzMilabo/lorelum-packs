# 上下文丢失后先重读决定下一步的事实

## 适用场景

同一任务或 Agent 在上下文压缩、中断或长时间暂停后恢复，只剩摘要或部分记忆时使用。在编辑、扩展计划或报告进度前完成。已知暂停前应写 Checkpoint；结论来自另一个 Agent 时应验证交接。

## 具体指导

摘要只用于定位材料。重新打开当前用户要求、已接受 Issue 或规格、相关计划和决定、当前 branch 与 diff，以及记录的测试或审查结果。逐项核对下一步依赖的摘要声明，删除已失效假设，收窄没有证明的完成说法。写清当前目标、允许改什么、第一项未完成必需行为、哪些结果仍对应当前文件，以及下一步。只读到足以决定下一步，不必重扫整个项目。

## 反模式

用户要求从真实远程仓库安装。上下文压缩后摘要写“安装已完成，只剩清理”，仓库单测也全绿，开始重构看起来很合理。重读 Issue 和 diff 才发现只测了模拟传输层，真实远程路径从未运行；摘要把部分实现变成了完成。

## 原因

摘要保留连续性，却可能漏掉最关键的要求、文件变化或失败检查。重看具体材料能阻止遗漏继续支配工作和进度声明。

## 例外与边界

只有一个输出的微小任务可快速对照当前文件。旧结果检查的是同一文件和条件时仍可用。用户要求、Issue 和规格冲突时先问哪份决定当前工作；来自他人的声明走交接验证。

## 示例

parser 必须拒绝坏 token，并从截断声明恢复。恢复工作后，Agent 核对要求、diff 和结果，确认当前 commit 已通过有效语法与坏 token，但没有截断用例，于是报告“核心解析已验证；截断恢复未检查”，下一步补该用例，而不是清理代码。
