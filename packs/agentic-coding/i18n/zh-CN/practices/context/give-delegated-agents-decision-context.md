# 委派前把影响判断的上下文交给 SubAgent

## 适用场景

SubAgent 不只是机械执行，还要像主 Agent 一样判断范围或质量时使用，尤其当决定性信息藏在对话、早先审查或多份它不会主动找到的来源里。输入输出已经完全封闭的机械任务，只需直接说明即可。

## 具体指导

发送一份紧凑的 Context
Packet，包含目标结果、当前由哪条用户要求或已接受规格决定、相关仓库现状、必须保持的约束和非目标，以及已经接受或否决的选择。若接收者可能再次做出同一个局部合理选择，要附上否决原因。再写清文件或代码符号范围、应返回什么、它负责哪些检查、什么发现必须上报。大文档给链接，不全文粘贴。直到接收者能说清自己要判断什么、必须保留什么、不能擅自改什么才停止。

## 反模式

用户和主 Agent 已明确要求 Pack 案例必须像能力正常的 Agent 会犯的错，并否决 scheduler 案例，因为它生硬又看不出真实诱因。主 Agent 委派重写时只说“按计划改需求类 Practice”。计划虽提到真实性，却没有记录被否决的案例和理由。SubAgent 合理地沿用已有素材，润色 scheduler 并交回格式正确的文件，于是重复了用户刚推翻的决定。

## 原因

委派通过裁掉对话历史节省上下文，但判断质量依赖的不只是任务名。只保留会改变决定的信息和理由，才能避免看似合理但错误的选择，同时不要求每个 Agent 重放整段历史。

## 例外与边界

精确改名、固定文本替换等选择已封闭的任务不需要很长的任务说明。也不能倾倒完整对话记录、原始日志、密钥等敏感信息或无关探索；过多内容同样会埋住决定。接收者仍须检查当前文件和结果，Context
Packet 不能证明仓库没有变化。

## 示例

委派 CLI 安装器改动前，主 Agent 写明：“默认安装必须走官方 Registry，显式自定义 Registry 也必须工作；复用现有 Pack
validator 和 materializer；不要增加任意 URL 来源、镜像自动回退、认证插件或新缓存；保留输入上限和类型化错误。返回改动文件、聚焦测试，以及任何无法避免的契约变化。”接收者既能保留必需扩展性，也不会顺手造通用来源平台。
