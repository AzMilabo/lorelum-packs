# 依赖他人结论前先核对它覆盖了什么

## 适用场景

收到其他 Agent、贡献者、委派任务或并行工作的结论、测试结果或完成状态，而下一步依赖它们时使用。只核对会改变下一步的声明，不重做全部探索。同一 Agent 上下文恢复应重新立足事实；暂不影响决定的建议可明确保持暂定。

## 具体指导

列出会改变计划、代码、批准或完成报告的交接声明。逐项核对当前用户要求或已接受规格，确认发送者使用的 branch、文件、commit 或环境，并按风险查看引用结果；同时检查它完成后是否又有改动。判定声明可原样使用、只能支持更小范围、没有支持，或需要拥有需求的人决定。更新下一步后停止。

## 反模式

用户要求迁移能回滚有数据的数据库，专门负责该任务的 Agent 报告“迁移已验证”，测试摘要也干净。完整测试数据运行很慢，主 Agent 直接准备交付看似合理；但引用结果只覆盖早先 commit 的正向迁移，当前 branch 又修改了回滚处理，两项限制都没写进交接。

## 原因

交接会压缩证据、假设和未知，接收方仍对下一项决定负责。聚焦核对可保留大部分委派速度，同时捕获遗漏范围、旧 commit 和过度自信。

## 例外与边界

低影响建议可暂定；commit 和行为明确的可信自动结果只需少量检查。安全、迁移、发布和破坏性声明需要更强核对。发送者不能仅凭交接改变范围，必须追到用户、维护者或已接受规格。

## 示例

共享存储不可用时，限流仍须正确。委派任务报告修复已验证，接收方检查 commit 和输出，只确认单进程突发限流，未见共享存储故障切换，于是保留单进程结果，拒绝“生产修复已验证”，把故障切换设为下一项检查。
