# 继续工作前先验证交接

## 适用场景

在跨 Agent 或跨贡献者的信息边界上，当接收方即将依据报告的发现、结果或完成状态采取行动时，应用本条 Practice。仅仅因为同一 Agent 在上下文丢失后恢复会话并不适用；交接内容不包含与下一项决策相关的结论时也不适用。

## 具体指导

找出下一项行动所依赖的交接声明，然后将它们与权威需求、当前产物状态和引用证据进行比较。接受、收窄、拒绝或上报每项依赖声明，并丢弃因并发变更而过时的假设。最终得到一项已验证的交接处置和一项修正后的下一步行动，然后停止。

## 反模式

交接声称“所有检查均通过”，但只引用了组件测试，而且当前分支已经改变验收所要求的集成路径；接收方仍直接继续工作。

## 原因

交接会同时压缩证据和不确定性，而产物可能独立变化。验证既能保留委派的价值，又能防止信心差异、信息遗漏或时间差作为虚假共享状态传播到主任务中。

## 例外与边界

低影响的探索性建议在成为决策输入前，可以保持明确的暂定状态。通过交接传递的权威范围变更，应作为权威变化处理，而不是仅因为另一个 Agent 报告了它就予以接受。

## 示例

一项委派任务报告安装已经验证。接收方确认了所引用的本地安装结果，但没有发现升级证据，于是把声明收窄到全新安装，并把升级验证保留为下一项行动。
