# 解决冲突来源之间的权威归属

## 适用场景

当两个或更多来源对预期行为有不同暗示，而 Agent 必须选择需求基线时，应用本条 Practice。来源可能是当前用户指令、已采纳的规格、Issue、决策记录、代码状态、摘要或更早的对话。如果这些来源彼此一致，问题仅在于现有代码是否可复用，则应检查实现，而不是应用本条 Practice。

## 具体指导

针对存在争议的要点，将每个相关来源分类为当前权威、历史事实或观察事实、未经确认的解释，或者已被取代的证据。依据明确采纳关系、授权纠正的新近程度，以及项目规定的治理方式来选择当前权威；仅凭细节多寡或时间先后都不足以做出判断。记录最终的权威决策及其解决的冲突。如果现有规则无法裁定一项重大的产品行为，应向有权决策的人提出这一未决选择，并在将其固化到实现之前停止。

## 反模式

一份简短摘要称审计记录一年后到期，而已采纳的保留策略要求保存七年。因为摘要更短就据此继续，会把派生来源置于需求权威之上。

## 原因

将权威与观察分开，可防止当前代码、旧决策和 Agent 生成的说明因反复出现而获得需求地位。这也让后续纠正保持局部：被取代的来源仍可作为历史记录使用，但不再支配新的工作。

## 例外与边界

当治理策略明确授予这种优先级时，紧急的安全或数据保护约束可以暂时覆盖权威级别较低的产品指令；应记录该覆盖及其适用范围。本条 Practice 决定哪个来源定义意图，不决定是否应复用某项实现，也不决定新设计是否更优。

## 示例

当前清理任务会在一年后删除审计记录，但获批的保留策略要求保存七年。应把该策略记录为需求权威，把任务调度记录为当前状态证据，而不是目标行为。
