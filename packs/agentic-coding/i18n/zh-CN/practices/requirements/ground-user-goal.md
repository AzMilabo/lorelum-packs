# 让工作立足于用户目标

## 适用场景

当 Agent 即将界定或继续一项工作，却没有一条当前有效的陈述说明谁需要什么可观察结果时，应用本条 Practice。这可能发生在任务开始时，也可能发生在实现细节已经开始取代工作初衷之后。如果结果已经清楚，唯一悬而未决的问题只是如何判断完成，则应改为定义验收边界。

## 具体指导

阅读用户当前的请求，以及任何已被明确采纳的任务来源。产出一条简洁的目标陈述，说明受影响的用户或操作人员、他们需要的可观察结果，以及任何会改变该结果的明确约束。把拟议的组件、抽象、测试和文档视为手段，而不是目标。如果某项重大歧义可能导向不同的用户结果，应标明该歧义或请求决策；不要通过自行选择一种实现来消解歧义。当结果陈述已经具体到足以排除那些无助于推进目标的工作时停止。

## 反模式

把“帮助客服人员定位延迟订单”转化为“构建状态仪表盘”，会让一种便于实现的界面形态变成目标。即使仪表盘能够正常渲染，客服人员仍可能无法根据他们收到的客户参考编号找到订单。

## 原因

稳定的结果陈述为后续的范围和设计决策提供共同参照。它能防止实现惯性和易于量化的产物悄然取代用户价值。

## 例外与边界

对于结果已经精确的纯机械性请求，例如重命名一个给定标签，用户的措辞本身可能已经是完整的目标陈述。不要额外增加规划仪式。本条 Practice 用于识别期望结果；它不负责枚举验收测试或非目标。

## 示例

在规划订单支持功能的变更前，记录：“客服人员可以通过客户参考编号定位订单并查看其当前配送状态，同时不会获得编辑订单的能力。”这样，就可以排除拟议中的分析仪表盘，因为它无助于推进该结果。
