# 先说清用户真正要得到什么

## 适用场景

任务刚开始，或做着做着已经只剩组件、文件和测试，却没有一句话说明“谁需要看到什么结果”时，使用这条 Practice。如果结果已经清楚，只是不知道怎样才算完成，应转去定义验收标准。

## 具体指导

重读用户当前要求，以及已经接受的 Issue 或规格。用一句话写清受影响的人、他最终能观察到的结果，以及会改变结果的明确限制。组件、测试、文档和抽象都只是可能的手段。若两种理解会带来不同结果，先请用户决定。写到这句话足以排除无助于结果的工作就停。

## 反模式

客服要用客户提供的编号找到延迟订单。仓库里恰好已有一个漂亮的运营看板，Agent 便在看板上加“延迟”标记，组件测试也都通过。这个选择很顺手，也能快速展示进度，但客服仍无法用客户给的编号搜索订单。

## 原因

明确的用户结果能让后续范围和设计都有同一个比较标准。否则，仓库现有结构和容易展示的产物会悄悄取代用户真正需要的能力。

## 例外与边界

如果请求本身已经非常精确，例如只把一个给定标签改名，用户原话可能就是完整目标，不必增加规划仪式。本条 Practice 只确定结果，不负责列验收项和非目标。

## 示例

用户要求改善上传失败体验。Agent 没有直接修改现成的通用错误横幅，而是先写下：“创作者能看出哪个文件失败，并只重试该文件，不必重新上传已经成功的文件。”这句话保留了 UI 方案空间，也说明为什么只换提示文案不够。
