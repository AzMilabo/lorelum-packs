# 每个测试都要说明自己保护哪项承诺

## 适用场景

新增或大改测试、仍在选择测试目的时使用。先问“这个测试失败，说明项目答应的哪件事可能坏了”。找到一项明确承诺后本条结束；怎样观察它属于断言设计，历史缺陷是否值得永久测试属于回归保护判断。

## 具体指导

指出测试依据：用户要求中的一句话、已接受 Issue 或规格、已发布接口，或“一个用户不能读取另一个用户数据”这类必要规则。把它改写成不提当前辅助函数或类的行为。只有测试失败确实意味着该行为可能坏掉时才保留，并在测试名、附近注释或审查说明中写清联系。没有真实理由时省略，或标为临时调查。

## 反模式

用户要求任务重试不能重复提交。改动新增队列 adapter、重试辅助函数和状态枚举，每个方法都容易测，覆盖率还突出其分支，于是 Agent 为每个方法写测试。测试全绿，却没有任何一个保护“同一任务重试时不得提交两次”。

## 原因

测试通常活得比当前实现选择更久。若目的来自代码结构，它会把错误设计固化得很完整；对应到真实承诺，维护成本和失败信号才有意义。

## 例外与边界

探索性探查和临时特征测试可揭示未知行为，但要标记并有意退役或转正。安全、兼容和数据完整性规则即使未写进产品文案，也可能值得覆盖。已有映射清楚的机械更新不必重复分析。

## 示例

上传必须在执行进程重启后继续且不损坏文件。Agent 为“重试中断分块不会重复写入字节”和“进程重启后上传能继续”各写一项测试，不测试分块辅助函数的调用顺序；下一步再选择可观察的存储和恢复结果。
