# 将每项测试锚定到契约

## 适用场景

在决定一项新增或修改后的测试要保护什么时，应用本条 Practice。关键决策是该测试要保护的行为或不变量。随后选择具体观察或断言方式，属于近似但不同的场景。决定是否以永久回归保护来记录一次历史失败，也属于另一个近似场景，需要单独判断其持久性。保持既有明确契约不变的机械性测试清理，不需要建立新的映射。

## 具体指导

针对拟议测试，找出一项违反后会造成实质影响的权威需求、已发布契约或领域不变量。用独立于当前实现的方式表达受保护行为，然后只有在测试的通过或失败能切实代表该行为时才纳入测试。输出是一项明确的测试到契约映射。如果找不到持久依据，应修改测试目的或省略该测试，而不是把代码发生变化本身当作充分理由。

## 反模式

为每个新增组件、方法、分支或状态都照样增加测试，尽管这些结构可能编码的是对用户能力不完整或错误的解释。

## 原因

测试会变成持久证据和未来变更约束。把每项测试锚定到需求或不变量，可以让测试套件与预期行为保持一致，避免当前实现自行定义何为正确。

## 例外与边界

探索性 probe 和临时特征测试可以帮助揭示未知行为，而无需立即断言该行为正确；应为它们加上明确标记，并有意识地退役或转为正式测试。即使安全、兼容性和数据完整性不变量没有出现在功能描述中，也可能足以支撑测试。本条 Practice 不规定断言机制。

## 示例

Agent 不为每个新增重试 helper 都增加测试，而是把拟议测试映射到“对一次瞬时失败重试一次，且不会重复执行操作”。没有独立契约的 helper 不会仅因被新增就获得测试。
