# 检查失败后先判断谁错了，再改代码或测试

## 适用场景

某项检查出现具体失败，且产品、测试、环境、非确定性、不同源码生成的文件或既有无关失败都可能解释时使用。在修改实现、预期、测试数据、生成文件或工具配置前暂停。没有复现的外部审查意见应先验证发现。

## 具体指导

用已知 commit、构建或生成文件复现最小失败。阅读断言或诊断，把实际行为与当前要求比较，并检查会影响结果的环境、输入、测试数据和生成文件。只收集足以区分主要解释的事实，记录错在哪里，以及哪项事实排除了第二可能解释，再选择修复。仍不清楚时不要改到变绿，报告未知。

## 反模式

用户要视觉刷新但保留键盘导航，附近 UI 重构让快照变化，新页面也很漂亮。更新快照只需一个命令并能恢复绿色，立刻接受很合理；但重构同时删掉必需键盘动作，这次更新会抹掉唯一失败信号。

## 原因

失败只证明两个状态不一致，不证明哪边错。先分类能避免把产品缺陷洗成新预期，也避免为满足旧测试而破坏正确行为。

## 例外与边界

延迟会扩大伤害时可先遏制安全、数据丢失或生产事件，并保留后续证据。已直接确认的基础设施故障或损坏生成文件可以修。需求变更使测试过时时，依据必须是获批变更，而不是新实现输出。

## 示例

数据库迁移测试单独通过，接在另一套测试后失败。Agent 改变执行顺序并检查起始 schema，发现前一套测试遗留共享状态；全新数据库迁移正常。因此问题是测试环境隔离，确认后才修改清理逻辑。
