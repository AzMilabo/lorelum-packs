# 要求回归保护具备证据依据

## 适用场景

在把一项已分类回归或权威纠正永久加入项目验证表面之前，应用本条 Practice。触发条件是判断保护是否应持久存在，而不是为当前需求编写普通正向覆盖。未分类失败属于近似但不同的场景，必须先分类，再考虑回归保护。已经记录为持久约束的安全禁令、兼容性边界或明确验收条件也不适用，因为其依据已经成立。

## 具体指导

识别拟议保护，并要求它至少具备一项持久依据：明确契约、可观察的“必须不存在”要求、确实发生且有可信复发风险的回归，或高影响的安全、隐私、兼容性或数据完整性边界。根据该依据，决定保留、收窄、限时保留或省略保护。输出是一项保护决策及其理由；近期犯过一次错误，本身不足以证明项目需要永久规则。

## 反模式

移除一段未经请求的文本后，增加永久断言，要求该确切文本永远不能再次出现，尽管用户只要求恢复原设计，并未建立任何新禁令。

## 原因

测试和门禁会把历史转化为未来的维护义务。要求持久理由，可以保留那些防止实质伤害的保护，同时避免规则集合不断记录每次已放弃的探索或局部纠正。

## 例外与边界

未授权访问、secret 暴露、破坏性数据丢失、监管违规和已发布兼容性破坏，即使只发生一次可信事件，也可能值得加入保护，因为失败成本很高。迁移期间也可以采用临时保护，但其移除条件必须明确。不要仅为减少测试数量或缩小 diff 而拒绝保护。

## 示例

Agent 移除一个未经请求的 tooltip，并拒绝增加“tooltip 永远不得存在”的测试。但它会为未授权访问增加拒绝路径测试，因为“访问必须不存在”是一项明确的安全契约。
