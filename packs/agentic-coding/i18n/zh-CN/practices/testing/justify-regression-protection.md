# 永久回归测试必须有长期理由

## 适用场景

失败或纠正已经查清，准备把它变成永久测试或门禁时使用。这里判断防复发是否值得长期维护，不再判断失败原因，也不是从当前需求直接选择普通正向测试。

## 具体指导

先说清拟议保护会捕获什么失败。只有存在长期理由时保留：明确承诺、必须不存在的行为、真实且可能复发的缺陷，或高影响的安全、隐私、兼容和数据完整性风险。决定永久、收窄、临时或省略，并用最小稳定结果捕获复发，不冻结当前辅助函数设计。记录理由；临时保护还要写移除条件。“刚发生过”不够。

## 反模式

用户只要求恢复一个被 Agent 擅自加辅助文字的页面。仓库已有文本检查机制，添加全局禁词很便宜，也让纠正显得彻底；但用户没有禁止全产品出现该文字，也不存在共享生成器或复发路径。一次局部恢复被写成永久产品禁令。

## 原因

回归测试和门禁会把单次事件变成长期约束。耐久性判断保留真正会复发且代价高的保护，避免测试套件只记录最近 Agent 犯过什么错。

## 例外与边界

未授权访问、密钥等敏感信息暴露、破坏性数据丢失、监管违规和公开兼容性破坏，单次可信事件也可能值得保护。迁移可加有明确移除条件的临时措施。不能为减少测试数量拒绝有依据的保护，也不能在原因未查清前添加。

## 示例

支付重试必须最多扣款一次。已复现缺陷是队列序列化器在重投前丢失请求 ID，重复扣款可能在未来重构中回来。Agent 增加永久测试：重投保存的任务后观察只有一笔扣款，而不固定现有队列辅助函数顺序。
