# 提交前执行减法审查

## 适用场景

当完整 diff 即将成为 commit 或交给他人审查，而且可以整体判断其中的新增内容时，应用本条 Practice。不要在实现过程中选择设计方案时应用，也不要把它变成缩小 diff 的要求——如果现有 diff 已经只包含有依据的工作，就无需强行缩小。

## 具体指导

逐项检查每个实质性新增内容，看它是否有当前需求、已证明风险、稳定契约或必要实现依赖作为依据。删除没有当前理由的新增内容，合并重复逻辑，并用已经适用的现有能力替换局部重复实现，同时保留证据支持的行为和保护。最终得到仍满足已接受结果及其风险边界的最小 diff，然后停止。

如果任何删除或替换可能影响已接受行为，则受影响的证据已经过期；在修订后的状态获得当前验证前，不得提交。

## 反模式

把删除数量当作成功指标，随后因为能让 patch 更小，就移除明确要求的扩展点或授权检查，却保留一个仅因看起来符合惯例而存在的不必要 helper。

## 原因

实现过程会积累各自在局部看似合理的额外内容，而在 diff 边界把它们作为整体观察更容易发现。减法审查可以减少没有依据的表面和维护成本，同时避免用最小化代替正确性。

## 例外与边界

当当前契约或 rollout 状态要求时，应保留看似未使用的迁移、兼容性、安全、审计或回滚机制。如果简化会改变公共契约或已接受架构，应把该决策交回适当的权威，而不是在清理阶段直接删除。

## 示例

一次提交前审查移除了第二个日期规范化 helper 和未使用的 fixture export，改用现有 parser，并保留批量大小 guard 和恢复标记，因为导入契约要求两者都存在。
